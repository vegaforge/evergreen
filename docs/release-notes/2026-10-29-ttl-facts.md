# TTL facts and the inclusive threshold

Contract authors now read what the Soroban host actually does. Nothing about
how Evergreen behaves on chain has changed; the code was already right and the
docs were not.

- An entry is extended when its remaining TTL is **at or below** the policy
  threshold, not strictly below it. The rustdoc, both READMEs, the book and the
  example comments now say so.
- Asking for more than the network's maximum TTL is capped by the host for
  persistent and instance entries, not a trap. The `TtlPolicy::resolve` rustdoc
  explains why Evergreen still caps first: it keeps the threshold at or below
  the target, and it keeps the same policy safe for a temporary entry, where the
  host does return an error.
- The docs no longer quote "about 30 days" as the maximum. The maximum is a
  network parameter; `docs/src/state-archival.md` says how to read it
  (`env.storage().max_ttl()` on chain, `stellar network settings` off chain),
  notes that `max_ttl()` is `max_entry_ttl - 1`, and gives the 2026-10-29
  mainnet and testnet values as a dated example.
- `PersistentStore::get` no longer claims an extending read joins the
  read-write footprint. A testnet run showed the key stays read-only while its
  TTL is raised and rent is charged.
- The example policies explain why a 30-day top-up is still a sensible target
  when mainnet's minimum for a new persistent entry is about 120 days.

Technical shape: four new tests in `crates/evergreen-core/src/tests.rs` cover
remaining TTL exactly at the threshold and one ledger above it, for
`PersistentStore` and `InstanceStore`, with their snapshot files. No public
API, function body or storage layout changed, so there is no semver impact and
no action for contracts already using Evergreen.
